# Go producer-authentication shadow

The private prototype now identifies clean native Go edit results that match an
independent fresh parse, while **keeping the fresh verifier active**. Two new
72-edit chains on Cognociente's original 140,368-byte source produce **144
would-certify observations and 144 real verifier observations** across the plain
and profiled APIs. Native incoming and fresh trees match structure, states and
internal precedence. This is a
correctness qualification step, not a new speed result or permission to bypass
verification. Runtime, ledger, admission and main merges remain unchanged.

The exact Go9ad artifact grants a generic capability through runtime profiles;
engine code does not branch on the language name. Actual default DFA ownership,
source identity, fresh scheduling policy and complete read history remain
separate requirements. Every new small-source schedule, alias and frontier
choice is capability-gated. Copy, transformed `+`→`-` factories, identity
wrappers, actual compact producers and absent capabilities must not certify.
This qualifies the default native producer only; compact-produced old trees
still need an independent producer contract.

## Extended clean edit chains

Each API uses its own native old-tree chain. Every chain grows and shrinks local
identifiers at 16 sites spread from function f0 to f1759. All 72 edits change the
source length by one byte; the final source returns to its exact original SHA.
These are additional clean sessions, separate from the two original R4 sessions.

Every step records a genuine native producer key, one actual verifier event,
one would-certify decision, strict incoming/fresh equality before replacement,
strict final/fresh equality, and zero no-edit allocations. Each incoming tree
shares 1,761 top-level node pointers with its actual edited old tree. Profiled
steps also report nonzero reused subtrees and bytes. Plain API profile counters
remain unavailable/zero; pointer identity supplies its separate reuse evidence.
The inherited Copy, transformed-factory, wrapper, compact and absent-capability
controls again produce zero would-certify decisions.

The offline validator reconstructs all 144 edits from the pinned source, checks
each byte offset/length/hash and reported decision, and matches both API chains.
It validates executed test results and their strict source assertions; it does
not rerun the parser or infer new C/fleet/platform coverage from these sessions.

## Preserved failure and identical baseline control

V1's strict compact-origin negative fails on an internal precedence comparison.
The identical control is then run on canonical baseline, candidate and a
candidate differing only by the Go capability being off. All three preserve the
same failure: **7,037 internal dynamic-precedence differences**, zero ParseState
or PreGotoState differences, identical whole-tree state hashes and exact fresh
public structure. Native-origin controls match every plane in every arm.
The original failed assertions and logs remain archived; this difference is not
repaired or relabeled as a passing strict-fresh comparison.

After that causal proof, test-only V2 requires unsupported compact results to
match the complete capability-off cross-producer result and independent fresh
public structure, with no small mode, native producer key or would-certify grant.
Every native would-certify comparison still requires absolute fresh structure,
state and precedence equality. No native assertion or runtime rule is weakened.

## Complete-operation work: six default edits still regress

The unchanged 3,254-byte `recovery-work-main.go` capture is retained byte for byte
with its source hash. It measures public fresh Parse plus owned release, or
Tree.Edit plus the profiled incremental API and both owned releases, including
internal verification/retry attempts. Both original declaration and assignment
fixtures exercise insert/replace/delete on both routes: **24 records per arm**.

All **12 fresh operations and six candidate edits have identical complete work**.
The six default edits increase total table lookups **0.342–1.026%**. That small
overall percentage includes the unchanged full verifier: the incremental phase's
own lookup work rises **24.85–28.29%**. These overlapping scopes are reported
separately; they do not establish a speed improvement.

| Default edit | Whole-operation table lookups | Incremental-phase table lookups |
| --- | ---: | ---: |

| Declaration delete | 1,024,644→1,028,175 | 12,803→16,334 |
| Assignment delete | 1,029,376→1,032,901 | 14,185→17,710 |

Declaration delete also adds four shifts, lexer/action visits and leaf
constructions; assignment delete adds two. Their selected reuse falls:
subtrees **1,769→1,765 / 1,763→1,761**, bytes **136,787→136,776 /
134,736→134,729**, and splices **3,538→3,534 / 3,526→3,524**. Selected allocation
and policy/cap differences are retained in every raw comparison, including the
six candidate edits whose work matches. Those selected arena values are not
benchmark B/op or a memory-win claim.

The validator recomputes every row and field difference from the four raw logs,

These new adverse events and reuse directions are also **unapproved**; the
assignment correctness exception does not cover them. The counter gate stays
failed, with no timing, ledger update, verifier removal or promotion.
